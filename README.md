# customer-support-ops — 客服營運的分析與交棒決策

把客服對話資料整理成可分析的形狀，回答兩個問題：**這通諮詢本來該不該發生**，
以及**該在第幾輪把對話交給人**。

![Version](https://img.shields.io/badge/version-0.1.0-blue.svg)
![License](https://img.shields.io/badge/license-MIT-green.svg)

> **v0.1.0 只有文件，沒有任何可執行程式碼。** 本版交付的是資料契約、推導規則、
> 里程碑與出口條件。實作從 M1 開始。

---

## 主張

> **交棒門檻不是準確率問題，是排程問題**——早轉浪費人力，晚轉浪費的是客戶耐性，
> 而後者不進任何報表。

客服分析的常見產物（工單量、分類分布、SLA 達成率）是現況描述不是分析，
等同客服系統內建的報表。這個專案把力氣放在兩個能撐起主張的地方：

1. **上游歸因** — 這通諮詢本來該不該發生。結論通常落在產品、物流或文案，不在客服。
2. **交棒決策** — 該在第幾輪把對話交給人。產出是一張**旋鈕掃描表**，不是一個最佳解。

## 功能特色

- **對話事件契約**（`data/contract.md`）— 分析層與決策層唯一的資料介面，換資料源不必改分析
- **推導欄位自報身分** — 交棒點、是否解決這類推導值一律帶 `rule_id` 與四態信度，
  報表引用時必須顯示它是推導的，不得寫成事實
- **假設全部登記在案**（`docs/ASSUMPTIONS.md`）— 每條推導規則都寫明「會在什麼情況下錯」
- **決策層輸出取捨不輸出答案** — 給定交棒門檻 T，輸出人工回合數／未解決率／
  客戶重複描述次數，讀者自己挑 T

## 資料來源與它的限制

主資料源為 Kaggle [Customer Support on Twitter](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter)
（thoughtvector），約 300 萬則推文、20 多個品牌客服帳號。
原始資料**不進 repo**（體積與授權，見 `docs/ASSUMPTIONS.md` §3）。

選它是因為 `in_response_to_tweet_id` 可重建完整對話串、`inbound` 分得出誰在等誰，
而且天然多品牌——跨商家比較不必另找資料源。

**四個不會因為做得更仔細而消失的限制**（詳見 `docs/ASSUMPTIONS.md` §4）：

1. 資料是 2017 年的
2. 公開推文不是後台工單，帳務與個資類客訴不會出現在這裡
3. 轉私訊之後發生什麼事，這份資料永遠答不了
4. 沒有任何成本資料，人力與等待成本只能由參數注入

還有兩個**結構性硬限制**，直接決定了這個專案的做法：資料裡**沒有 bot／真人標籤**，
也**沒有工單解決狀態**。因此「交棒點」與「是否解決」在這裡是隱藏變數，
只能靠行為訊號反推——這正是 `docs/ASSUMPTIONS.md` 存在的理由。

## 快速開始

v0.1.0 沒有可執行的東西。目前的「跑起來」是讀四份文件，順序如下：

```bash
# 1. 這個專案在主張什麼、為什麼這樣切
cat prepare.md          # 決策記錄 CS-000～CS-008

# 2. 資料長什麼形狀
cat data/contract.md    # 對話事件契約

# 3. 哪些東西是猜的
cat docs/ASSUMPTIONS.md # 推導規則、參數、待查證清單

# 4. 分層與里程碑出口條件
cat docs/ARCHITECTURE.md
```

M1 落地後，這一節會換成取得資料 → 建契約表 → 跑驗證的三行指令。

## 使用方式

同上，v0.1.0 尚無。M1 的預期入口為 `scripts/`（取得與驗證）與 `analysis/`（指標）。

## 專案結構

```
customer-support-ops/
├── data/contract.md      對話事件契約（跨層唯一介面）
├── docs/
│   ├── ARCHITECTURE.md   四層職責、資料流、里程碑與出口條件
│   └── ASSUMPTIONS.md    推導規則、參數、待查證、資料本身的限制
├── prepare.md            決策記錄 CS-000～
├── CLAUDE.md             專案規則（技術棧、資料層硬規則）
└── CHANGELOG.md
```

`scripts/`、`analysis/`、`decision/`、`figures/` 在對應里程碑才建——
**不預先建空資料夾**，空目錄看起來像做過了。分層說明見 `docs/ARCHITECTURE.md`。

## 開發階段

| 里程碑 | 交付 | 砍掉的條件 |
|--------|------|-----------|
| **M1** 數據整理 | 契約表、基準線、30 串人工標註 | 串接失敗率 > 5% → 資料撐不住，止損 |
| **M2** 優化流程 | 上游歸因、`FINDINGS.md` | 得不出反直覺結論 → 停在 M1 收尾 |
| **M3** 跨商家橫向 | 品牌基準比較 | 解釋不了離群值 → 只是排行榜，退回 M2 |
| **M4** 單一商家縱深 | 挑一家做深的診斷 | 建議都是「多請人、回快點」→ 縱深沒有加值，砍 |
| **M5** 人機交棒決策 | 旋鈕掃描表 | M1 的交棒訊號關卡沒過 → **本里程碑不存在** |

**M1 有一道前移的關卡**：30 串人工標註要能穩定標出「第幾輪交棒」。
標不出來，M5 直接從規劃中砍掉、專案定位改為「客服營運分析」，而且會寫在這裡，不是默默不做。
把最大風險的驗證放進第一個里程碑，是因為 M5 是這個專案的差異化核心，
排在最後等於讓最值錢的部分最可能做不到。

完整出口條件見 `docs/ARCHITECTURE.md`。

## 測試

v0.1.0 無測試。M1 落地後，第一個檢查是 `scripts/validate.py`：
契約表若有任何一列的推導欄位缺 `rule_id` 或 `confidence`，即判定不合格、不准往下跑。
